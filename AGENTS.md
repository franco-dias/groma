# Groma: guide for agents

Read this before changing anything. It is the context a new maintainer
needs and the rules that keep the project working.

## What this is

Groma is a Figma-style inspector for web pages: design handoffs, local builds and staging apps (the name is the
Roman surveyor's instrument). The npm package is `gromajs` (npm refused `groma` as too close to existing
names); in prose, write
"Groma" for the product and "the inspector" for the thing on the page. One script, added to any
HTML page, lets an engineer hover and pin elements to read their box model,
specs, design tokens and distances.

- **Users**: engineers on any project and any stack who build from an HTML
  design handoff, often one generated by an AI design tool, or who change an
  app that already exists. Do not
  assume a framework or a design system when you add a feature.
- **Describe the design; do not write the code.** The inspector reports
  what the design uses: values, tokens, a component's name and the props
  the design passes. It must not present anything as "the line to paste",
  because it cannot know a project's component API. JSX suggestions were
  removed for this reason; do not bring them back.
- **Defaults assume nothing about the project.** Values copy as plain CSS
  and no token naming convention is built in. What a project does
  differently is a setting (`src/config.ts`), never a default. Knowledge of
  one framework lives in one component reader (`src/specs/components/`),
  which must return null on pages it does not understand. If you are about
  to write the name of a framework or a design system outside those two
  places, stop: it belongs in a setting or a reader.
- **How it ships**: `dist/groma.js`, one self-contained file, to be
  served from a CDN and attached to design pages or to an app's dev build.
- **Where it runs**: inside pages we do not control. This shapes most of
  the rules below.

What each feature does, with the rules it must keep, is in
[docs/features.md](docs/features.md). The file map, the scripts and the
release steps are in [docs/development.md](docs/development.md); settings
and known limits are in [docs/usage.md](docs/usage.md). Read the feature's
section before you touch it.

The README is the first read for a newcomer: context, motivation, how to
try it. Keep it short; detail belongs in `docs/`.

## Commands

```bash
npm run serve        # demo page with live reload
npm run inspect -- <file.html>   # any HTML file with the inspector attached
npm test             # unit + browser tests
npm run typecheck
npm run build        # typecheck, then dist/groma.js
npm run lint         # oxlint: the limits of the code style (.oxlintrc.json)
npm run format       # oxfmt: formats the code, styles and docs in place
```

Before you say a change is done: `npm test`, `npm run build`, `npm run lint`
and `npm run format:check` all pass.
The browser tests need Google Chrome installed; they do not download one.

## Code style

The code follows the owner's `franco-style` skills (TypeScript, testing,
errors and sanitization, delivery; the React ones do not apply here). Load
them before writing or reviewing code. Where they and this file differ, this
file wins. The formatter owns the layout: never format by hand. The linter
keeps the limits a tool can check: functions of 20 lines at most, files of
100, two parameters, one level of nesting, no nested ternaries, no `any`, no
`!`, no `null` where `undefined` will do.

- A rule is switched off only on the line that needs it, with the reason:
  `// oxlint-disable-next-line <rule> -- <why>`. The usual reasons are the
  DOM (it answers `null`) and the compatibility contracts below
  (`pinnedElement()` answers `null`).
- The panel's markup (`*.html`) is laid out by hand and is not formatted.

## Rules

### The script is a guest on someone else's page

1. **No runtime dependencies and no frameworks.** The build must stay one
   file with nothing to load. React was considered and rejected for size;
   do not add it, or any dependency that ends up in `dist/`, without the
   owner asking.
2. **All UI lives in the shadow root.** Create top-level nodes with
   `mount()` from `src/root.ts`. Never append inspector nodes to the page's
   DOM, and never add styles to the page.
3. **One global: `window.Groma`.** Nothing else on `window`.
4. **Do nothing until the user inspects.** With Alt up and the lock off,
   the page must behave exactly as without the script. The only standing
   UI is the launcher pill.
5. **Never change the page except for the user's own edits**, and keep what
   the page had so Reset can restore it (`src/edits/style-overrides.ts`,
   `content-overrides.ts`). One
   exception, by design: in push mode the panel sets an inline `margin-right`
   on `<html>`, remembers the page's value and puts it back when the panel
   closes (`src/page-shift.ts`). Do not add other page changes.
6. **The page changes under you.** Pages re-render and replace elements;
   boards render late; `<body>` may not exist yet at start. Check
   `isConnected`, use `whenBodyExists`, and never assume an element found
   earlier is still there.
7. **Fail quietly, never break the page.** Storage can be blocked,
   stylesheets can be cross-origin, the clipboard can refuse. Catch these
   where they happen and carry on.

### The page may be in a frame

In canvas mode (`src/canvas/`) the inspected page is the document of a
frame, not `document`. `src/page.ts` knows which one it is.

- Read the page with `pageDocument()` and `pageWindow()`, never `document`,
  `window` or `location`. Those are for the inspector's own UI.
- Listen to the page with `onPage()` and `onPageWindow()`: they follow the
  frame's document as it loads and changes.
- Place overlays with `rectOf(el)`, which answers in this window's screen
  pixels. `el.getBoundingClientRect()` answers in the frame's own pixels:
  right for a value shown in the panel, wrong for a position on screen.
- Mount anything that marks the page with `mountOnPage()`, so the canvas
  cuts it at the frame's edge.
- Do not use `instanceof` on a node, a rule or an event from the page: the
  frame has its own `Element`, `SVGElement` and `CSSStyleRule`. Use
  `isElement()` or check a property.

### Shadow DOM gotchas

- An event that starts inside the inspector reaches `document` listeners
  with the host element as its target. Use `isOwn(target)` to skip the
  inspector's own UI, and `event.composedPath()` when you need the real
  target.
- `document.querySelector` does not see the inspector's nodes. Hold
  references, or query the shadow root.
- The host is a manual popover, in the browser's top layer, so no page
  element can cover it (`src/root.ts`). Do not give the host a `transform`
  or `overflow`, and do not take it out of the top layer: a page that uses
  the highest z-index would then hide the panel.

### Pixels

- Boards are shown zoomed with CSS transforms. `getBoundingClientRect()`
  is in screen pixels; computed styles and `offsetWidth` are in board
  pixels. Use `scaleOf()` and `layoutSize()` from `src/dom.ts`; never mix
  the two by hand.
- Anything shown to the user (sizes, distances, positions) is in board
  pixels.

### Architecture

- `src/main.ts` only starts features. Features do not import each other's
  internals.
- The pinned element lives in `src/selection.ts`. Code that picks an
  element calls `pin()`; code that shows it subscribes with
  `onSelection()`. After an edit or an option change, call `rerender()`.
- A panel tab implements `Tab` (`src/panel/tab.ts`) and is listed in
  `src/panel/panel.ts`. It is one file, or an entry file with sibling modules
  in its own folder (`src/panel/specs/`, `css/`, `edits/`, `changes/`). Tabs do
  not import each other, and a tab's modules are not imported from outside its
  folder.
- A user's edit to the page goes through `edit()`, `nudgeEdit()` or
  `removeEdit()` in `src/edits/changes.ts`, so it is saved, listed in the
  Edits tab and can be undone.
- Logic that needs no page (formatting, parsing, comparing) goes in
  `src/specs/` or a plain module, with a unit test beside it.
- Markup goes in `src/panel/panel.html`; styles in `src/styles/`. Do not
  build static markup or set static styles from TypeScript.

### Design

- Colours, spacing, radii and fonts come from the variables in
  `src/styles/tokens.css`. Do not write a colour or a spacing value
  anywhere else.
- Type sizes are 10, 11, 12 and 13px only; weights 400, 500, 600. Labels
  are sans-serif, values monospace. Hierarchy comes from colour and
  spacing, not size.
- The panel must work between 320 and 560px wide with no horizontal
  scroll.
- Feedback must not move things: copy marks and states add no size.
- The panel slides in and out (`--ins-dur-slide`). The browser tests switch
  the slide off in `tests/helpers.ts`, because they read the panel the moment
  it opens or closes; `slidePanel()` turns it back on for a test.
- The source design is the "Inspector States" file (not in this repo). The
  product departs from it on purpose in four places, which the owner knows;
  do not "fix" them:
  - the All CSS tab stays an editable list of computed properties;
  - hover keeps the coloured box-model overlay, with the name chip;
  - the collapsed panel is a rail that expands on click, with no tab
    sticking out of its edge;
  - a distance label that does not fit its line moves beside it,
    alternating sides.

### Tests

- A behaviour change and its test go in the same commit. A bug fix comes
  with the test that would have caught it.
- Browser tests (`tests/`) drive the inspector as a user does and read its
  UI. Use the helpers in `tests/helpers.ts`; call `reset()` in
  `beforeEach`, because the inspector is one instance per test file.
- The outline and the grid are placed on animation frames: `await
  frames()` before measuring them.
- Do not weaken a test to make it pass. If a test is wrong, say why in the
  commit.
- After writing a test for a fix, break the fix once and confirm the test
  fails.

### Compatibility you must not break silently

- **`window.Groma`** (`GromaApi` in `src/main.ts`): host pages call it.
  Removing or changing a method is a major version.
- **Names in the page**: the host element is `<groma-inspector>` and the
  script tag marker is `data-groma`. Pages and tests select them.
- **The `gromajs` command** and its options (`--copy`, `--token-prefix`,
  `--port`, `--no-open`): people type them. Renaming one is a major version.
- **Settings** (`data-copy`, `data-token-prefix` and `configure()`): pages
  in the wild carry these attributes. Changing a default or a value's
  meaning is a major version.
- **Storage keys**: `__groma_overrides:<path>`,
  `__groma_html:<path>`, `__groma_before:<path>`, `__groma_notes:<path>`,
  `__groma_panel` and `__groma_canvas`. Renaming
  one loses users' saved edits; migrate, or do not rename.
- **The text "Copy edits" writes** (`src/edits/handoff.ts`): agents and
  people's prompts read it. Keep its headings and the shape of its lines, or
  say what changed in the changelog.
- **Saved selectors** (`src/edits/selector.ts`): changing their shape
  orphans saved edits.
- **Claude Design export format**: `BOARD_SELECTOR`, `#dc-data` and the
  `@ds-bundle` header are read as they are today. If an export changes
  shape, support both shapes.
- **React internals**: the React reader uses `__reactFiber$…`. It is
  unofficial; keep it defensive and never let it throw.

### Writing

- Every source file opens with a comment that says what the feature does
  for the user. Keep it true when you change the file.
- Comments explain why, in plain English. A known limit is marked
  `shortcut: <the limit>, <when to upgrade>`; keep those markers.
- Update [docs/features.md](docs/features.md) and
  [CHANGELOG.md](CHANGELOG.md) with the change.
- The in-product reference (`src/panel/reference.html`) is what users read.
  When you add or change a shortcut, a click target or a setting, change
  its line there in the same commit.

### Releasing

- Versions follow semver; `npm version` bumps, commits and tags.
- The code is MIT licensed and the package is public on npm. Do not run
  `npm publish`, push a tag or change the licence unless the owner asks:
  a published version cannot be reused.

## Known limits

Listed in [docs/usage.md](docs/usage.md). The ones most likely to bite:

- Token lookup takes the last matching declaration and ignores selector
  specificity (`src/page-styles.ts`).
- Sizing intent is inferred; grid children are treated as plain blocks.
- The colour picker is Chromium-only and has no test.
- Tests run in Chrome only, with synthetic events.
- Elements inside the page's own iframes and other shadow roots are not
  inspected.
- The canvas loads the page a second time. A `file://` page, or one whose
  server forbids framing, is shown from a copy of the open page, on which
  the page's scripts run again.

## Trying a change on a real handoff

The demo page (`npm run serve`) covers most cases. For a real file:

```bash
npm run inspect -- path/to/export.html --no-open
```

It serves the file with the built inspector attached and does not edit it
(`scripts/inspect.mjs`, Node built-ins only). The same script ships in the
package as the `gromajs` command (`npx gromajs <file.html>`), so it must keep
working from an installed package: only Node built-ins, and every file it
imports listed in `files` in `package.json` (`scripts/package.test.mjs`). Exports render boards only
when they scroll into view.
